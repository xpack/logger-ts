### v7.0.0

**Breaking change:** the package is now an **ES module only**; the
CommonJS build, with the ES6 wrapper of v6, was removed.

**Breaking change:** the minimum Node.js version is now **22.12**, the
first version of the 22 line that loads ES modules with `require()` by
default (the previous versions fail with `ERR_REQUIRE_ESM`). ES module
projects need no change. CommonJS projects can keep using
`require('@xpack/logger')` on Node.js 22.12 or later, or use
`await import('@xpack/logger')`.

**Breaking change:** the `Logger` constructor no longer logs the line
`trace: Logger.constructor()` when the log level is `trace` or `all`. If
your tests counted the lines captured by a mock console, or compared them
with the lines of the previous versions, remove this line from the expected
results.

The `package.json` file is now exported, so tools can read it through the
package name (`@xpack/logger/package.json`); this is not a breaking change.

The TypeScript module resolution mode `node10`, which ignores the `exports`
map, is still supported through the legacy `main` and `typings` fields of
`package.json`, but it is **deprecated**: **support for `node10` will be
removed in a future major release**. Projects that use it, usually the
ones with `"module": "commonjs"` and no explicit `moduleResolution`,
should migrate to `node16`, `nodenext`, or `bundler`. This is not a
breaking change in this version.

**Breaking change:** an invalid log level, passed to the constructor, to
the `level` setter, or to `isLevel()`, now throws a `RangeError` (for a
string that is not a level name) or a `TypeError` (for a value that is not
a string), with a message that lists the valid names, instead of an
`AssertionError` with the message `Log level 'xyz' not supported.`
(or, for an empty value, the generic message `The expression evaluated to
a falsy value`). Code that catches `AssertionError` to detect an invalid
level must catch these errors instead; to avoid the exception, check the
value first with the new `Logger.isLogLevel()`.

**Breaking change (compile time only):** the type of the `level` setter is
now `LogLevel`, not `LogLevel | undefined`, so TypeScript code that assigns
`undefined` to `log.level` no longer compiles. Such an assignment was
already rejected at run time (with a `TypeError` since this version), so
the code was wrong; to use a level that may be missing, check it with
`Logger.isLogLevel()` first. The getter still returns
`LogLevel | undefined`. The `level` and `console` constructor options now
accept an explicit `undefined`, also with `exactOptionalPropertyTypes`,
which is not a breaking change.

The `console` option of the constructor now accepts any object that has the
`log()` and `error()` functions (the new exported type `LoggerConsole`),
not only a Node.js `Console`, so a mock or a minimal `{ log, error }` object
no longer needs a cast. The `Logger` class has a new type parameter, the
type of the console, which the `console` accessor returns; its default is
the Node.js `Console`, so the existing code is not affected (this is not a
breaking change).

The `isSilent` accessor was deprecated (this is not a breaking change).
Since `silent` is the lowest level, it was always `true`, for every level,
so it could not tell whether the logger is silent. It will be removed in
the next major version.

If used, replace it with a comparison of the log level name:

```javascript
if (log.level === 'silent') {
  // ...
}
```

### v6.0.0

The TypeScript code is compiled into
**CommonJS** modules, with an **ES6** wrapper, and can be consumed by both
TypeScript and JavaScript packages.

There were also some minor internal renames, but this should not be
a problem.

The function `isLevel(level)` was added.

### v5.0.0

For consistency reasons, `hasLevel` was changed from a method to an
accessor.

Internally, the log level starts as `undefined` instead of the
string `'undefined'`, as in previous versions.

This should not be a problem, given that the method to check if
the level was set is via `hasLevel()`.

### v4.0.0

The code was migrated to TypeScript.

The migration itself should not introduce any incompatibilities,
actually it should be fairly compatible with the latest v3.x,
but, for just in case, the safer path was to consider it a major
release.

### v3.0.0

All `isXyx` functions (returning a boolean related to
the log level) were changed to accessors.

### v2.0.0

The logger constructor was changed to use a generic
parameters object.

If upgrading from previous versions, change the syntax from:

```javascript
const log = new Logger(console, 'info')
```

to:

```javascript
const log = new Logger({
  console,
  level: 'info'
})
```
