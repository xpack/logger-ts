The `@xpack/logger` module can be imported into both TypeScript
and JavaScript Node.js code.

In TypeScript and ECMAScript modules, use `import`:

```typescript
import { Logger } from '@xpack/logger'
```

In JavaScript with CommonJS, use `require()`:

```javascript
const { Logger } = request('@xpack/logger')
```

The module can be included in any application and the class can be used
directly or a custom class can be derived from it for a custom behaviour.

The typical use case is to create an instance of the `Logger` object,
then log messages at different levels:

```javascript
const log = new Logger({
  level: 'info'
})

log.info('hello') // Displayed on stdout.
log.debug('world') // Ignored.
```

In more complex use cases, the log level can be tested and the (possibly)
long operations be performed only if necessary.

### Log levels

The following strings are recognised as valid level names:

```typescript
export type LogLevel =
  'silent' | 'error' | 'warn' | 'info' | 'verbose' | 'debug' | 'trace' | 'all'
```

Internally, string levels are converted to integer values for comparison
purposes. Higher integer values correspond to greater verbosity.

The valid names, in increasing order of verbosity, are available at run
time as the frozen array `Logger.levelNames`.

When the level comes from a source that is not checked by the compiler,
like a command line option or an environment variable, validate it with
the type guard `Logger.isLogLevel()`, which narrows the type of its
argument to `LogLevel`. It returns `false` for non-string values, for
strings with a different case (`'INFO'`), and for the names of inherited
properties (`'toString'`):

```typescript
const name = process.env.LOG_LEVEL
if (Logger.isLogLevel(name)) {
  log.level = name
} else {
  log.error(`Level must be one of: ${Logger.levelNames.join(', ')}`)
}
```

Assigning an invalid name to `log.level`, or passing it to the
constructor, throws an `AssertionError`.

### Delaying setting the log level

In some cases, the logger needs to be initialized very early in the
application's lifecycle, even before the log level can be determined.

In such cases, if the logger is initialized without a specified log level,
it enters a **preliminary state**. During this time, all log entries are
stored in an **internal buffer**. Once the log level is set, the buffer
is processed, and the log entries are handled accordingly.

```typescript
const log = new Logger()
log.trace('...') // Not shown immediately
log.level = 'trace' // Set level and show the buffered messages.

log.info('hello') // Displayed on stdout.
log.debug('world') // Ignored.
```

Nothing is written while the logger is in the preliminary state, not even
the messages of `always()` and `error()`. If the log level is never set
(for example when the application fails before it determines the level),
the buffered messages are never written and are lost. Set the log level on
every path, for example in a `catch` block, using `hasLevel` to check
whether it was set:

```typescript
try {
  // Determine the log level, then set it.
  log.level = parseLevel(process.argv)
} catch (err) {
  if (!log.hasLevel) {
    log.level = Logger.defaultLevel
  }
  log.error(err)
}
```

The buffer is emptied before the messages are written, so each buffered
message is written at most once. If the console throws while the buffer
is flushed, the exception is propagated from the level setter, the level
remains set, and the buffered messages that were not yet written are
discarded.

### Output methods

The following methods are available to log messages:

- `always (message: any = '', ...args: any[]): void`
- `error (message: any = '', ...args: any[]): void`
- `error (message: Error): void`
- `output (message: any = '', ...args: any[]): void`
- `warn (message: any = '', ...args: any[]): void`
- `info (message: any = '', ...args: any[]): void`
- `verbose (message: any = '', ...args: any[]): void`
- `debug (message: any = '', ...args: any[]): void`
- `trace (message: any = '', ...args: any[]): void`

### Logging errors

`Error` objects are expanded by `util.format()`, as by `console.log()`:
the first line has the name and the message (for example `Error: boom`),
and it is followed by the stack trace and, if present, the `cause` chain,
on several lines. This is the same in all output methods, which differ
only by the stream and the prefix.

The caller decides how much of an error is shown:

- to show the full details, including the stack trace, pass the error
  object, for example `log.error(err)`;
- to show a single line, pass only its message, for example
  `log.error(err.message)`.

The prefix depends on the method and on the position of the error:

| Call | Output (first line) | Stream |
| --- | --- | --- |
| `log.error(err)` | `Error: boom`, then the stack trace | stderr |
| `log.error('failed:', err)` | `error: failed: Error: boom`, then the stack trace | stderr |
| `log.error(err.message)` | `error: boom` | stderr |
| `log.warn(err)` | `warning: Error: boom`, then the stack trace | stderr |
| `log.output(err)` | `Error: boom`, then the stack trace | stdout |
| `log.output(err.message)` | `boom` | stdout |
| `log.debug(err)` | `debug: Error: boom`, then the stack trace | stdout |

Only `error()` omits its prefix, and only when the error is the first
argument, since the first line of the expanded error already starts with
its name.

A common pattern is to show the message at the `error` level, and the full
details only when the log level is `debug` or higher. It also works in the
preliminary state, since both messages are buffered and filtered when the
log level is set:

```typescript
try {
  // ...
} catch (err) {
  // On stderr: `error: boom`.
  log.error(err instanceof Error ? err.message : String(err))
  // On stdout, only at `debug` or higher: `debug: Error: boom`,
  // followed by the stack trace.
  log.debug(err)
}
```

In TypeScript, the variable of a `catch` clause has the type `unknown`,
hence the `instanceof` check. To also keep the name of the error, use
`String(err)` instead of `err.message`: `log.error(String(err))` outputs,
for example, `error: TypeError: boom`.

### Log level checks

When preparing the log messages is expensive, it makes no sense to
do it and call the output method to simply return if the log level
is low and the message is not needed.

Instead, the log level can be checked explicitly:

```typescript
if (log.isDebug) {
  const message = invoke_long_method()
  log.debug(message)
}
```

When the log level is not known at compile time, use the generic
`isLevel(level)` method, which returns `true` if the current log level
is equal to the given level or higher.

Before a log level is set (the preliminary state), all checks
(`isDebug`, `isLevel()`, and the others) return `true`. This way, the
messages produced under the check are stored in the internal buffer
rather than lost, and are filtered when the log level is set. Use
`hasLevel` to tell whether a log level was set.

For example, to ensure that the log level is not decreased, check
`hasLevel` first, since in the preliminary state there is no level
to compare with:

```typescript
if (!log.hasLevel || !log.isLevel(newLevel)) {
  log.level = newLevel
}
```

The `isSilent` accessor is deprecated, since it is always `true`; to
check for the `silent` level, use `log.level === 'silent'`.
